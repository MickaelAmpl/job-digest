# Full QA of the deployed bot - 09.10.2026

7 testers + 7 skeptic verifiers on a snapshot of /opt/job-digest (no Telegram, no server changes). Severity after verification. Repro scripts: scratchpad/fulltest/<area>/ (session scratchpad).

## MAJOR (confirmed)
### data-1: Unrelated jobs are silently closed as 'duplicate' when the found original link is a listing or API page
- Area: store.mark_if_duplicate / score.save (real-data evidence) | file: store.py
- Expected: Three different RWA jobs stay three jobs. same_link() should treat only a link that identifies one posting as 'the same job'.
- Actual: Three unrelated jobs whose enrich 'original_url' was https://jobs.rwa.at/ei/services/getJobOffers/stepstone: the first stays, the other two get closed=1, closed_by='duplicate', and are never delivered (digest.pending returns only 'Product Owner Agrar'). same_link() only rejects paths with 1 or fewer segments, so a 4-segment API endpoint passes. The real DB already holds one such open_url (RWA, row 63f2952332). The next RWA job whose enrich returns the same URL disappears with no trace.
- Repro: python3 <scratch>   (real row for evidence: sqlite3 data/state.db "select id,open_url from jobs where id='63f2952332'")
- Verifier: Reproduced in verify-data (dup_false_pos copy): 3 different RWA jobs sharing the original_url https://jobs.rwa.at/ei/services/getJobOffers/stepstone, two end closed=1/closed_by=duplicate, and only 'Product Owner Agrar' is pending. same_link() only rejects paths with fewer than 2 segments. Real DB row 63f2952332 already holds exactly that generic API open_url, so the next RWA/StepStone job with the same enrich result is silently lost. Needs enrich to return the same generic URL twice, but the mechanism is concrete and the data already shows it.

- Area: input robustness / hostile feed | file: fetch_companies.py, collect.py, store.py (remember), score.py (save)
- Expected: A bad character in one job is cleaned or that job is skipped; the other jobs and the morning go on. The tailoring code already scrubs surrogates (cv/tailor/checks.scrub) but the rest of the pipeline does not.

- Repro: cd .../fulltest/security && python3 scripts/t11_surrogate.py  (feed title 'Product Manager \ud83d'); python3 scripts/t6b_score_surrogate.py  (fake claude returns why_ru 'bad \ud800 char' for 1 of 61 jobs). A JS-truncated emoji or a deliberate '\ud800' in a job ad is enough.

The damage when it fires is large: all company feeds are lost every day until that job leaves the feed. Not a blocker, since the trigger is rare. Note: the first-run lock on score.main in my test was an artefact of my uncommitted transaction.

### security-02: A single oversized field in one alert email makes prefilter.py crash and stops scoring for 2 mornings
- Area: email parser / pipeline | file: collect.py (parse_linkedin/parse_stepstone write CSV), prefilter.py (load_trial csv.DictReader), run.sh
- Expected: A hostile or broken mail loses at most its own job; prefilter, prepare, enrich and score still run.

Anyone who can land a mail in the inbox with a display name containing e.g. 'jobs.at' can trigger it (see security-05).
- Repro: python3 scripts/t17_e2e_bigmail.py (a LinkedIn-style mail with one 200 KB line -> collect.main() -> prefilter.main()); bash scripts/t16_setE.sh shows that a failing 'step' under set -e aborts the rest of run.sh.

Impact if it fires is high: scoring stops for the 2-day mail window. Rated major rather than blocker because of the hostile-only trigger.

### security-03: One inbox mail with an unknown charset or deep MIME nesting kills ALL email job collection
- Area: email parser | file: collect.py (fetch_alert_emails, text_part)
- Expected: The bad message is skipped (logged) and the other mails are parsed. A non-job sender should never be able to break the run.
- Actual: The From header of EVERY inbox message from the last 2 days is decoded before the sender check, with no per-message try/except. LookupError/RecursionError escapes fetch_alert_emails, main() prints 'email collection failed' and continues with mails=[]: LinkedIn, StepStone, karriere.at, derStandard and jobs.at are dropped for the whole lookback window. Only the log shows it; the digest does not mention it. Plain spam with a real-world charset name is enough, no attacker needed.
- Repro: python3 scripts/t4_email.py  cases a, b, e. Header check: str(make_header(decode_header('=?windows-874?q?abc?= <s@s.com>'))) raises LookupError; same for iso-8859-8-i, x-user-defined, x-mac-cyrillic, cp-850, x-sjis. Also a job-sender mail with Content-Type charset=x-bogus, and a 3000-level nested multipart (RecursionError).
- Verifier: Reproduced. A From header with encoded-word charset windows-874, iso-8859-8-i, x-mac-cyrillic, cp-850 or x-sjis makes make_header/str raise LookupError (Python 3.10; I could not run 3.12 here). There is no per-message try/except, so main() logs 'email collection failed' and continues with mails=[]. A nesting depth of 3000 gives RecursionError, but a depth of 400 is fine. Unlike the other hostile-only findings, a real foreign-language newsletter in the inbox can trigger this. Email alerts (LinkedIn and StepStone) are a core source, per the logs. Adzuna and company feeds still run, so it is a degradation, not a total outage.
